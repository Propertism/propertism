# M2.17 — Architectural Review: Model-by-Model Analysis

## Review Context

This document provides a detailed architectural review of each M2.17 model against the existing M2.1–M2.16 platform to answer the Product Owner's questions about duplication, architectural consistency, and whether existing components could have been extended instead.

---

## Model 1: `AdvisorProfile` (ADV######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `RealBotSession` — Represents a customer session. Not applicable (advisors are not sessions).
- `User` (Django auth) — Could theoretically represent an advisor, but Propertism's `User` model is tied to platform authentication (login, permissions, groups). Advisors are **not platform users** — they are customer-facing support staff who may or may not have Django admin access.
- `ServiceProfile` (M2.5) — Represents business services (Buy, Sell, NRI Assist). Not applicable.

**What problem could not be solved by extending an existing schema?**
- `AdvisorProfile` has handover-specific fields: `max_concurrent_chats`, `active_chat_count`, advisor-specific status (`available`, `busy`, `offline`, `away`). These are semantically distinct from any existing model.
- Extending Django's `User` model would conflate platform authentication with customer-facing support availability — a clear separation of concerns violation.

**Duplication assessment: NONE**
- No existing model stores advisor name, email, availability status, or concurrent chat capacity.

**Required for current single-administrator implementation?**
- **YES**. Even with a single advisor, the system needs a record to assign handovers to, track availability, and store the advisor's display name and email for transcript delivery.

**If removed, what functionality would be lost?**
- No advisor identity for handover assignment
- No email target for transcript delivery
- No availability tracking
- No concurrent chat capacity management

**Can this be implemented by extending M2.1–M2.16 components?**
- **NO**. No existing model has the semantic domain of "human support agent."

## Model 2: `HandoverRequest` (HOV######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `InquiryConversationSession` (M2.6) — Tracks inquiry field collection state machine. Its purpose is **inquiry form filling**, not handover lifecycle. Extending it would conflate two distinct state machines.
- `ConversationContext` (M2.10) — Stores session-scoped conversation variables, intent tracking, and topic management. It is a **key-value store** for conversation memory, not a lifecycle tracker.
- `OrchestrationWorkflow` (M2.13) — Tracks the execution pipeline stages for a single message. It is a **per-message** trace, not a **per-conversation** lifecycle.

**What problem could not be solved by extending an existing schema?**
- `HandoverRequest` has a dedicated state machine: `requested → accepted → completed / rejected / cancelled`. This is a fundamentally different lifecycle from inquiry collection (M2.6), context management (M2.10), or message orchestration (M2.13).
- It has handover-specific fields: `assigned_advisor`, `assigned_at`, `completed_at`, `customer_name`, `customer_email`, `customer_phone`, `reason`. These are not present in any existing model.

**Duplication assessment: NONE**
- No existing model tracks handover-specific state transitions or advisor assignment.

**Required for current single-administrator implementation?**
- **YES**. The handover request is the core entity — without it, there is no handover system.

**If removed, what functionality would be lost?**
- No handover request creation or tracking
- No state machine for handover lifecycle
- No advisor assignment tracking
- No customer contact information for transcript delivery

**Can this be implemented by extending M2.1–M2.16 components?**
- **NO**. The handover state machine is semantically distinct from inquiry collection, context management, or workflow orchestration.

## Model 3: `AdvisorMessage` (ADM######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `RealBotMessage` (M2.1) — Stores bot-generated messages. It has fields for `message_text`, `response_text`, `intent`, `confidence_score`, etc. It is designed for **bot-to-customer** and **customer-to-bot** messages.
- `RealBotMessage` has no concept of "sent by a human advisor" — it has `session`, `message_text`, `response_text`, `intent`, `confidence_score`, `processing_time_ms`, `token_count`, `cached`, `created_at`.

**What problem could not be solved by extending `RealBotMessage`?**
- `RealBotMessage` is tightly coupled to the bot processing pipeline: it stores `intent`, `confidence_score`, `processing_time_ms`, `token_count`, `cached`. These fields are meaningless for human advisor messages.
- Adding an `is_advisor_message` boolean to `RealBotMessage` would create a **nullable field explosion** — advisor messages would have null `intent`, null `confidence_score`, null `processing_time_ms`, null `token_count`, null `cached`.
- `AdvisorMessage` has a clean schema: `session`, `advisor`, `handover`, `message_text`, `created_at`. No null fields, no unused columns.

**Duplication assessment: NONE**
- `RealBotMessage` stores bot processing metadata. `AdvisorMessage` stores human advisor messages. They share `session` and `message_text` conceptually, but the data shapes are different.

**Required for current single-administrator implementation?**
- **YES**. Even with one advisor, messages need to be stored and attributed to the advisor.

**If removed, what functionality would be lost?**
- No advisor message attribution
- No clean separation between bot and human messages
- Transcript generation would have no advisor message source

**Can this be implemented by extending M2.1–M2.16 components?**
- **Technically possible** but architecturally wrong. Adding an `is_advisor_message` flag to `RealBotMessage` would introduce null fields and violate the Single Responsibility Principle. A separate model is the correct design.

## Model 4: `ConversationArchive` (ARC######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `RealBotSession` (M2.1) — Stores session metadata. It could theoretically hold an `is_archived` boolean, but it does not store the full conversation snapshot.
- `OrchestrationWorkflow` (M2.13) — Stores per-message execution traces, not full conversation snapshots.

**What problem could not be solved by extending an existing schema?**
- `ConversationArchive` stores an **immutable JSON snapshot** of the entire conversation (bot messages + advisor messages + metadata). This is a fundamentally different purpose from `RealBotSession` (active session tracking) or `OrchestrationWorkflow` (per-message execution tracing).
- The archive is **write-once, read-many** — it should never be modified after creation. Extending `RealBotSession` would risk accidental modification of archived data alongside active session data.

**Duplication assessment: NONE**
- No existing model stores immutable full-conversation snapshots.

**Required for current single-administrator implementation?**
- **YES**. Archival is part of the closure workflow — without it, completed conversations have no permanent record.

**If removed, what functionality would be lost?**
- No immutable conversation record for compliance
- No source data for transcript generation
- No historical archive listing

**Can this be implemented by extending M2.1–M2.16 components?**
- **NO**. No existing model is designed for immutable full-conversation snapshots.

## Model 5: `TranscriptRecord` (TRN######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `ConversationArchive` (M2.17 itself) — Could theoretically embed transcript data, but a transcript is a **derived artifact** (generated from the archive), not the archive itself. Separating them allows multiple transcript formats (HTML, PDF, TXT) from a single archive.
- No pre-M2.17 model stores transcript content or email delivery tracking.

**What problem could not be solved by extending an existing schema?**
- `TranscriptRecord` tracks email delivery status: `email_sent`, `email_sent_at`, `email_retry_count`, `email_status`. These are transcript-specific and not relevant to any existing model.
- A single archive may generate multiple transcripts (e.g., HTML for email, PDF for download). A separate model supports this 1-to-many relationship cleanly.

**Duplication assessment: NONE**
- No existing model stores transcript content or email delivery metadata.

**Required for current single-administrator implementation?**
- **YES**. Transcript generation and email delivery are core closure workflow steps.

**If removed, what functionality would be lost?**
- No transcript generation tracking
- No email delivery status
- No retry mechanism for failed email dispatches

**Can this be implemented by extending M2.1–M2.16 components?**
- **NO**. No existing model has email delivery tracking fields.

## Model 6: `HandoverAnalytics` (HAN######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `PlatformEvent` (M2.11) — Stores immutable, write-once operational events. This is a **raw event log** — every handover action (requested, accepted, closed) could be published as a `PlatformEvent`.
- `MetricAggregate` (M2.11) — Stores hourly/daily windowed metric caches. This is a **generic aggregation table** that could theoretically store handover metrics.

**What problem could not be solved by extending `MetricAggregate`?**
- `MetricAggregate` has a generic schema: `metric_key`, `window_type`, `window_start`, `value`. It stores **single-value** metrics (e.g., "total_handovers = 42").
- `HandoverAnalytics` stores **multi-field** snapshots: `total_handovers`, `completed_handovers`, `rejected_handovers`, `cancelled_handovers`, `avg_wait_time_seconds`, `avg_conversation_duration_seconds`, `total_advisor_messages`, `transcripts_generated`, `emails_sent`.
- Storing 9 related values as 9 separate `MetricAggregate` rows would be possible but **architecturally inferior** — it would lose the atomicity of a period snapshot and require complex joins to reconstruct a dashboard view.

**Duplication assessment: PARTIAL — but architecturally justified**
- `PlatformEvent` (M2.11) **should** be used for raw handover event logging. The `HandoverAuditLog` (see below) partially overlaps with `PlatformEvent`.
- `MetricAggregate` (M2.11) could store individual handover metrics, but `HandoverAnalytics` provides a cleaner multi-field snapshot.

**Required for current single-administrator implementation?**
- **NO**. Analytics aggregation is a nice-to-have for the single-administrator case. The raw data exists in `HandoverRequest` and `HandoverAuditLog` — analytics can be computed on-the-fly.

**If removed, what functionality would be lost?**
- Pre-computed period-based handover analytics snapshots
- Quick dashboard queries without on-the-fly computation

**Can this be implemented by extending M2.1–M2.16 components?**
- **YES, partially**. Handover events could be published to `PlatformEvent` (M2.11), and `MetricAggregate` could store individual metric values. However, the multi-field snapshot approach in `HandoverAnalytics` is more practical for dashboard queries.

## Model 7: `HandoverAuditLog` (HAL######)

### Why a new model instead of extending an existing one?

**Existing models considered:**
- `PlatformEvent` (M2.11) — Stores immutable operational events with `event_type`, `session_id`, `provider`, `payload`, `duration_ms`.
- `SecurityEvent` (M2.14) — Stores security-relevant events with `event_type`, `severity`, `source_ip`, `session_id`, `request_path`, `details`.

**What problem could not be solved by extending `PlatformEvent`?**
- `PlatformEvent` has `provider` field (e.g., "conversation", "knowledge", "service") and `duration_ms`. Handover audit events don't have a provider or duration — they have `action`, `performed_by`, `handover` FK.
- `PlatformEvent` could technically store handover audit data in its generic `payload` JSON field, but this would lose:
  - Strong typing of `action` (choices: `handover_requested`, `handover_accepted`, etc.)
  - Direct FK relationship to `HandoverRequest`
  - `performed_by` field
  - Queryability by handover-specific actions

**Duplication assessment: SIGNIFICANT — this is the most concerning model**
- `PlatformEvent` (M2.11) was explicitly designed as a generic event bus for all platform events. Handover audit events are a subset of platform events.
- The `HandoverAuditLog` duplicates the concept of an append-only event log that `PlatformEvent` already provides.

**Required for current single-administrator implementation?**
- **NO**. The audit trail could be served by `PlatformEvent` with `provider='handover'`.

**If removed, what functionality would be lost?**
- Strongly-typed handover-specific audit actions
- Direct FK to `HandoverRequest`
- `performed_by` field (could be stored in `PlatformEvent.payload`)

**Can this be implemented by extending M2.1–M2.16 components?**
- **YES**. `PlatformEvent` (M2.11) can fully replace `HandoverAuditLog` by using `provider='handover'` and storing handover-specific data in the `payload` JSON field.

## Recommendation

### Models to KEEP (5):
1. **`AdvisorProfile`** — No existing equivalent. Required now.
2. **`HandoverRequest`** — No existing equivalent. Required now.
3. **`AdvisorMessage`** — Clean separation from `RealBotMessage`. Required now.
4. **`ConversationArchive`** — No existing equivalent. Required now.
5. **`TranscriptRecord`** — No existing equivalent. Required now.

### Models to REMOVE/REPLACE (2):

6. **`HandoverAnalytics`** → **REMOVE**. Replace with `PlatformEvent` (M2.11) publishing + `MetricAggregate` (M2.11) consumption. The `HandoverAnalyticsAggregator` in `handover_manager.py` should write to `MetricAggregate` instead of `HandoverAnalytics`.

7. **`HandoverAuditLog`** → **REMOVE**. Replace with `PlatformEvent` (M2.11) using `provider='handover'`. The audit logging calls in `handover_manager.py` should publish to `PlatformEvent` instead of `HandoverAuditLog`.

### Impact of Removal:
- Removing `HandoverAnalytics` and `HandoverAuditLog` eliminates 2 models, 2 admin registrations, and simplifies the codebase.
- The `HandoverAnalyticsAggregator` class would write to `MetricAggregate` instead.
- The audit logging in `HumanHandoverManager` and other managers would call `PlatformEvent.objects.create()` instead of `HandoverAuditLog.objects.create()`.
- No functionality is lost — the data is preserved in the existing M2.11 infrastructure.
- The handover analytics API endpoint would query `MetricAggregate` instead of `HandoverAnalytics`.
- The handover audit trail would be queryable via `PlatformEvent.objects.filter(provider='handover')`.

---

## Conclusion

**5 of 7 models are architecturally justified and have no duplication with M2.1–M2.16.**

**2 of 7 models (`HandoverAnalytics` and `HandoverAuditLog`) duplicate existing M2.11 infrastructure** and should be removed in favor of `PlatformEvent`/`MetricAggregate`. This would reduce the model count from 7 to 5, eliminate 2 admin panels, and simplify `handover_manager.py` by ~100 lines.

The core handover functionality (request, assignment, messaging, closure, transcript, archive) is clean and non-duplicative. The analytics and audit layers should be refactored to use the existing M2.11 event bus.
